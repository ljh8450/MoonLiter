# 자체 계정 신뢰성과 단계별 사용자 정지

## 목표

- 이메일/비밀번호 기반 자체 계정 로그인에서 이메일 인증 필수 정책을 적용한다.
- 회원가입 시 전화번호 인증을 도입하고, 인증된 전화번호 기준으로 중복 회원가입을 막는다.
- 관리자 정지 기능을 누적 정지 횟수 기반 단계별 정지 정책으로 확장한다.
- 정지 적용 시 사용자에게 앱 내부 알림을 제공한다.

## 맥락

- 현재 MVP는 React + Vite 웹앱, Supabase Auth, Supabase Postgres, Supabase Storage, Cloudflare Pages 배포를 기준으로 한다.
- 현재 구현은 소셜/이메일 로그인, 엽서 작성/수신, 신고, 관리자 승인, 기본 사용자 정지를 포함한다.
- 다음 구현 단위는 계정 신뢰성, 중복 가입 방지, 정지 정책, 정지 알림을 강화하는 흐름이다.
- 전화번호 인증은 Supabase Auth 기본 이메일 로그인보다 운영 범위가 크므로 SMS 제공자와 운영 정책 결정이 필요하다.

## 범위

- 이메일/비밀번호 가입 후 이메일 인증 완료 전 주요 기능 접근 제한.
- 전화번호 인증 기반 가입 흐름 설계 및 구현.
- 인증된 전화번호의 계정 단위 고유성 보장.
- 동일 전화번호 중복 가입 차단.
- 관리자 정지 시 누적 정지 횟수에 따른 정지 기간 계산.
- 정지 단계:
  - 1회: 1일
  - 2회: 7일
  - 3회: 30일
  - 4회: 1년
  - 5회 이상: 영구 정지
- 정지 사유, 정지 횟수, 정지 시작일, 정지 해제 예정일, 영구 정지 여부 저장.
- 정지 적용 시 앱 내부 알림 생성.
- 정지된 사용자의 주요 기능 접근 제한.

## 제외 범위

- SMS 제공자 계약, 과금, 운영 콘솔 설정의 실제 수행.
- 이메일/SMS 문구의 최종 마케팅 카피 확정.
- PWA 푸시 알림.
- 차단 기능.
- 계절 테마.
- 감성 태그.
- Android 코드 삭제 작업.
- Cloudflare Pages 운영 배포 적용.

## 작업

- [ ] 현재 이메일/비밀번호 가입과 로그인 흐름을 점검한다. - 검증: 이메일 인증 전/후 사용자 상태를 구분할 수 있는지 확인한다.
- [ ] 이메일 인증 미완료 사용자의 주요 기능 접근 제한 정책을 적용한다. - 검증: 미인증 계정은 엽서 작성, 오늘의 엽서 수신, 신고, 북마크 같은 로그인 기반 기능을 사용할 수 없다.
- [ ] 전화번호 인증 제공 방식과 저장 위치를 결정한다. - 검증: 인증된 전화번호가 사용자 계정과 1:1로 연결되는 데이터 모델이 정의된다.
- [ ] 전화번호 인증 UI/API 흐름을 설계한다. - 검증: 가입 중 전화번호 입력, 인증 요청, 인증 확인, 실패 재시도 흐름이 정리된다.
- [ ] 인증된 전화번호 기준 중복 가입 차단을 구현한다. - 검증: 이미 가입된 전화번호로 새 계정을 만들 수 없다.
- [ ] 정지 이력과 현재 정지 상태를 저장할 데이터 모델을 정리한다. - 검증: 누적 정지 횟수, 현재 정지 여부, 해제 예정일, 영구 정지 여부를 조회할 수 있다.
- [ ] 관리자 정지 처리 시 정지 기간을 자동 계산한다. - 검증: 1회, 2회, 3회, 4회, 5회 이상 정지에 대해 각각 1일, 7일, 30일, 1년, 영구 정지가 적용된다.
- [ ] 정지 해제 흐름을 정리한다. - 검증: 기간 만료 정지와 영구 정지를 구분하고, 관리자가 수동 해제할 수 있는지 확인한다.
- [ ] 정지 사용자 접근 제한을 적용한다. - 검증: 정지 사용자는 엽서 작성, 오늘의 엽서 수신, 신고, 반응 같은 주요 기능을 사용할 수 없다.
- [ ] 앱 내부 알림 데이터 모델을 정리한다. - 검증: 사용자별 알림, 알림 유형, 제목/본문, 읽음 상태, 생성 시각을 저장할 수 있다.
- [ ] 정지 적용 시 앱 내부 알림을 생성한다. - 검증: 정지된 사용자는 앱 안에서 정지 사유, 기간, 해제 예정일 또는 영구 정지 여부를 확인할 수 있다.
- [ ] 관리자 화면에서 정지 횟수와 현재 정지 상태를 확인할 수 있게 한다. - 검증: 관리자는 사용자별 누적 정지 횟수, 현재 상태, 해제 예정일을 확인할 수 있다.
- [ ] 관련 RLS와 권한을 점검한다. - 검증: 일반 사용자는 자신의 알림과 정지 상태만 볼 수 있고, 관리자는 필요한 관리 정보만 접근할 수 있다.

## 의존성

- Supabase Auth 이메일 인증 설정.
- 전화번호 인증을 처리할 SMS 제공자 또는 Supabase Phone Auth 사용 여부 결정.
- 사용자 프로필, 관리자 권한, 사용자 정지, 알림을 저장할 Postgres 스키마 변경.
- 프론트엔드 가입/로그인 화면과 관리자 사용자 관리 화면 변경.
- RLS 정책 변경.

## 미정 질문

- 전화번호 인증은 Supabase Phone Auth로 처리할지, 별도 SMS 제공자로 처리할지.
- 전화번호는 원문 저장, 정규화 저장, 해시 저장 중 어떤 방식으로 관리할지.
- 기존 가입 사용자는 전화번호 인증을 언제 요구할지.
- 소셜 로그인 사용자의 전화번호 인증을 필수로 둘지.
- 정지 만료 후 자동 해제는 조회 시 계산으로 처리할지, 예약 작업으로 처리할지.
- 영구 정지 계정의 동일 전화번호 재가입 시도는 어떤 메시지로 안내할지.

## 인계 항목

- 백엔드/DB: 전화번호 고유성, 정지 이력, 현재 정지 상태, 앱 내부 알림 스키마와 RLS를 설계한다.
- 프론트엔드: 이메일 인증 대기 상태, 전화번호 인증 가입 흐름, 정지 상태 화면, 앱 내부 알림 UI, 관리자 정지 UI를 구현한다.
- 운영/문서: SMS 제공자, 비용, 발송 제한, 전화번호 보관 정책, 개인정보 처리 문구를 정리한다.
- reviewer: 인증 우회, 정지 사용자 권한, 알림 조회 권한, 전화번호 중복 가입 우회 가능성을 점검한다.

## 완료 기준

- 이메일 미인증 사용자는 주요 기능을 사용할 수 없다.
- 인증된 전화번호가 없는 신규 사용자는 가입을 완료할 수 없다.
- 동일 전화번호로 중복 회원가입할 수 없다.
- 관리자가 사용자를 정지하면 누적 횟수에 맞는 정지 기간이 자동 적용된다.
- 정지 사용자는 주요 기능 접근이 제한된다.
- 정지 사용자는 앱 내부 알림으로 정지 사유와 기간을 확인할 수 있다.
- 관리자는 사용자별 정지 횟수, 현재 정지 상태, 해제 예정일을 확인할 수 있다.
