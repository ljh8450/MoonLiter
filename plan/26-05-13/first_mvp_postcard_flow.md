# 최우선 MVP 엽서 흐름 구현 계획

## 목표

사용자가 감성 문장을 담은 엽서를 작성하고, 다른 사용자가 오늘의 엽서로 받을 수 있는 최소 세로 흐름을 먼저 구현한다.

이 구현 단위는 새벽우체국의 핵심 경험인 "오늘의 마음을 누군가에게 보낸다"를 검증하는 첫 MVP 단위다.

## 맥락

- 현재 Android 앱은 홈과 엽서 작성 초안 UI만 존재한다.
- 현재 백엔드는 Spring Boot 골격, 공통 응답, 보안 설정, 헬스 체크, 사용자 엔티티와 `app_users` DDL만 존재한다.
- `postcard`, `delivery`, `media`, `reaction`, `theme`, `notification`, `admin`은 패키지 경계만 있고 실제 도메인/DDL/API는 아직 없다.
- 사진 업로드와 소셜 로그인은 중요하지만, 첫 구현 단위에 모두 포함하면 API, 저장소, 외부 연동, 검수 범위가 한 번에 커진다.

## 우선순위 판단

1. 핵심 제품 경험은 엽서 작성, 익명 전달, 수신이다.
2. 사진 업로드는 핵심 경험을 강화하지만, 텍스트 엽서 흐름이 먼저 있어야 연결 대상과 검수 상태가 정의된다.
3. 소셜 로그인은 운영 전 필수지만, 첫 로컬 MVP에서는 사용자 식별을 단순화해 도메인 흐름을 먼저 검증할 수 있다.
4. 반응, 저장, 신고, 차단은 수신 흐름 이후에 붙이는 확장 기능이다.

## 범위

- 백엔드 도메인 모델 초안
  - 엽서 작성자, 엽서 본문, 공개/검수/전달 상태, 생성 시각을 표현한다.
  - 오늘의 엽서 수신 이력을 표현한다.
- DDL 초안
  - `postcards`
  - `postcard_deliveries`
- 백엔드 API 초안
  - 엽서 작성
  - 발송 가능한 엽서 중 하나를 오늘의 엽서로 배정
  - 오늘의 엽서 조회
- Android 연동 초안
  - 현재 엽서 작성 화면의 `저장하기` 동작을 API 호출 대상으로 전환한다.
  - 오늘의 엽서 화면을 추가한다.
- 검증
  - 백엔드 테스트로 작성, 배정, 조회 흐름을 검증한다.
  - Android는 로컬 API 연결 또는 mock repository로 화면 상태 전환을 검증한다.

## 제외 범위

- Google, Kakao Talk, Apple 실 로그인 연동.
- presigned URL 기반 사진 업로드.
- 이미지 검증, 리사이징, 검수 자동화.
- 푸시 알림.
- 관리자 화면.
- 저장, 반응, 신고, 차단 기능.
- AWS, Docker, GitHub Actions 배포 구성.

## 작업

- [ ] 백엔드 담당: `postcards`, `postcard_deliveries` 최소 DDL을 설계한다 - 검증: `docs/ddl.sql`에 두 테이블과 인덱스가 정의되어 있고 기존 `app_users`와 외래키 관계가 명확하다.
- [ ] 백엔드 담당: 엽서 도메인 상태 값을 결정한다 - 검증: 작성됨, 전달 가능, 전달 완료, 숨김 또는 검수 제외 상태가 문서와 코드에서 같은 의미로 쓰인다.
- [ ] 백엔드 담당: 엽서 작성 API 계약을 정의하고 구현한다 - 검증: 유효한 사용자와 본문으로 엽서가 저장되고 빈 본문은 거부된다.
- [ ] 백엔드 담당: 오늘의 엽서 배정 API 계약을 정의하고 구현한다 - 검증: 자기 엽서는 배정되지 않고, 같은 사용자가 같은 날짜에 중복 배정받지 않는다.
- [ ] 백엔드 담당: 오늘의 엽서 조회 API 계약을 정의하고 구현한다 - 검증: 배정된 엽서 본문과 작성 시각을 익명 작성자 정보 없이 조회한다.
- [ ] 백엔드 담당: 첫 구현 단위에서는 인증을 단순화할 방식을 결정한다 - 검증: 임시 사용자 선택 방식 또는 테스트 사용자 생성 방식이 운영 인증과 충돌하지 않게 분리되어 있다.
- [ ] 프론트엔드 담당: Android 엽서 작성 화면을 백엔드 작성 API에 연결한다 - 검증: 입력한 문장이 API 요청으로 전송되고 성공/실패 상태가 화면에 반영된다.
- [ ] 프론트엔드 담당: 오늘의 엽서 화면을 추가한다 - 검증: 배정된 엽서가 있으면 본문을 보여주고, 없으면 조용한 빈 상태를 보여준다.
- [ ] 문서 담당: 첫 MVP API 계약을 문서화한다 - 검증: 요청/응답 예시, 인증 임시 방식, 주요 오류 케이스가 문서에 포함된다.

## 의존성

- `app_users` 테이블과 `AppUser` 엔티티는 첫 구현 단위의 사용자 기준으로 재사용한다.
- 백엔드 구현 전 `postcard`와 `delivery`의 책임 경계를 먼저 정해야 한다.
- Android API 연동은 백엔드 API 경로와 응답 형식이 확정된 뒤 진행한다.

## 미정 질문

- 첫 로컬 MVP에서 사용자를 어떻게 선택할지 결정해야 한다. 후보는 개발용 고정 사용자, 요청 헤더 기반 임시 사용자, 간단한 이메일 로그인이다.
- "오늘의 엽서"를 서버 날짜 기준으로 할지 사용자 로컬 날짜 기준으로 할지 결정해야 한다.
- 작성 즉시 전달 가능하게 둘지, 추후 검수 흐름을 고려해 기본 상태를 `PENDING_REVIEW`로 둘지 결정해야 한다.

## 완료 기준

- 한 사용자가 엽서를 작성할 수 있다.
- 다른 사용자가 오늘의 엽서를 배정받고 조회할 수 있다.
- 동일 사용자가 같은 날짜에 중복 수신하지 않는다.
- 작성자 식별 정보는 수신 응답에 노출되지 않는다.
- 백엔드 테스트가 핵심 흐름을 검증한다.
- Android에서 작성 화면과 오늘의 엽서 화면이 첫 MVP API 흐름과 연결될 준비가 되어 있다.

## 다음 인계

- 백엔드: 이 문서를 기준으로 DDL, 엔티티, API, 테스트를 구현한다.
- 프론트엔드: API 계약 확정 후 작성 화면 저장 동작과 오늘의 엽서 화면을 연결한다.
- 문서: 구현된 API 요청/응답 예시를 `/docs`에 반영한다.
