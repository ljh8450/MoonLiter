# 엽서 사진 업로드 MVP 구현 계획

## 목표

향후 Android 앱에서 사진 1장과 감성 문장을 함께 담아 엽서를 작성하고, 수신자가 오늘의 엽서에서 사진과 문장을 함께 확인할 수 있게 한다.

이 구현 단위는 README의 핵심 경험인 "직접 찍은 사진과 짧은 감성 글귀를 익명으로 전달"하는 흐름을 Android/Spring Boot 경로에서 구현할 때의 후속 계획이다.

## 맥락

- 현재 엽서 작성, 오늘의 엽서 배정, 오늘의 엽서 조회 API는 텍스트 기반으로 동작한다.
- Android 앱은 개발용 사용자 ID, 엽서 작성, 오늘의 엽서 화면과 API 클라이언트를 갖췄다.
- 상위 계획은 이미지 업로드를 presigned URL 기반 오브젝트 스토리지 직접 업로드 방식으로 잡고 있다.
- 첫 사진 업로드 MVP는 운영 완성형 미디어 파이프라인이 아니라, 단일 이미지 업로드와 엽서 연결이 실제로 되는지 검증하는 세로 흐름으로 제한한다.
- 현재 우선 구현 경로는 웹/Supabase MVP이며, 이 문서는 Android/Spring Boot 경로를 재개할 때 사용한다.

## 범위

- 백엔드 미디어 도메인
  - 업로드 대상 이미지의 storage key, content type, 크기, 업로드 상태, 소유자, 생성 시각을 저장한다.
  - MVP에서는 엽서당 이미지 1장만 허용한다.
  - 엽서와 이미지는 `postcards.media_file_id` nullable 컬럼으로 연결한다.
- 백엔드 API
  - 이미지 업로드 URL 발급 API.
  - 업로드 완료 등록 API.
  - 엽서 작성 API에서 업로드 완료된 이미지 ID를 선택적으로 연결.
  - 오늘의 엽서 응답에 앱이 바로 표시할 수 있는 `image.url`을 포함한다.
  - 서버 내부 저장소 식별자는 공개 URL이 아니라 `storage_key`를 기준으로 관리한다.
- Android UI/API 연동
  - 엽서 작성 화면에서 사진 1장을 선택한다.
  - presigned URL 발급, 이미지 PUT 업로드, 업로드 완료 등록, 엽서 작성 순서로 연결한다.
  - 오늘의 엽서 화면에서 이미지가 있으면 문장과 함께 표시한다.
- 문서
  - `/docs/ddl.sql`에 미디어 테이블과 엽서 연결 스키마를 반영한다.
  - `/docs/api.md`에 업로드 API와 변경된 엽서 요청/응답 예시를 반영한다.

## 제외 범위

- 다중 이미지 업로드.
- 이미지 리사이징, 썸네일 생성, EXIF 제거.
- 자동 검수, 수동 관리자 검수 화면.
- CDN, signed GET URL, 캐시 정책. 단, 응답 필드는 향후 signed GET URL로 전환해도 유지할 수 있게 `image.url`로 둔다.
- 업로드 취소, 재시도 큐, 백그라운드 업로드.
- 사진 필터, 보정, 크롭 편집.
- 운영 인증 전환.
- AWS 배포 자동화와 실 운영 버킷 정책 고도화.

## 현재 결정사항

- 클라이언트 응답에는 storage key를 직접 노출하지 않고, 앱이 바로 렌더링할 수 있는 `image.url`을 제공한다.
- DB와 서버 내부 로직은 `storage_key`를 원천 값으로 저장하고, 응답 URL은 요청 처리 시 생성한다.
- 엽서당 이미지 1장 MVP는 `postcards.media_file_id` nullable 컬럼으로 구현한다.
- `postcard_media` 연결 테이블은 다중 이미지, 이미지 순서, 대표 이미지 같은 요구사항이 실제로 생길 때 도입한다.
- 업로드 URL 발급 시 content type, byte size, 소유자를 검증하고 `PENDING` 상태의 미디어 레코드를 만든다.
- 업로드 완료 등록 시 media ID 존재 여부, 소유자, 현재 상태를 검증한다.
- 업로드 완료 등록 시 오브젝트 스토리지 `HEAD` 검증을 포함하는 방향을 기본으로 한다.
- 엽서 작성 시 `mediaId`가 있으면 본인 소유, `UPLOADED` 상태, 다른 엽서 미연결 여부를 검증한다.

## 작업

- [ ] 백엔드 담당: 미디어 저장 모델을 확정한다 - 검증: `media_files`와 `postcards.media_file_id` nullable 컬럼이 엽서당 이미지 1장 요구사항을 충족한다.
- [ ] 백엔드 담당: 목표 DDL을 설계한다 - 검증: `docs/ddl.sql`에 `media_files`, 상태 컬럼, `postcards.media_file_id`, 필요한 소유자/상태/연결 인덱스가 포함된다.
- [ ] 백엔드 담당: presigned URL 발급 API 계약을 정의하고 구현한다 - 검증: 사용자 ID, 파일명, 허용된 content type, 제한 내 byte size 입력으로 업로드 URL과 media ID가 반환되고 `PENDING` 상태가 저장된다.
- [ ] 백엔드 담당: 업로드 완료 등록 API 계약을 정의하고 구현한다 - 검증: 발급된 media ID가 오브젝트 `HEAD` 검증 후 `UPLOADED` 상태로 전환되고, 소유자 외 사용자는 완료 처리할 수 없다.
- [ ] 백엔드 담당: 엽서 작성 API에 선택적 media ID를 연결한다 - 검증: 업로드 완료된 본인 이미지이면서 다른 엽서에 연결되지 않은 경우만 연결되고, 미완료 또는 타인 이미지는 거부된다.
- [ ] 백엔드 담당: 오늘의 엽서 응답에 이미지 정보를 포함한다 - 검증: 이미지가 있는 엽서는 `image.url`이 응답에 포함되고, 이미지 없는 기존 엽서는 `image` 없이 계속 조회된다.
- [ ] 프론트엔드 담당: Android 엽서 작성 화면에 사진 선택 UI를 추가한다 - 검증: 갤러리에서 이미지 1장을 선택하면 작성 화면에 미리보기가 표시된다.
- [ ] 프론트엔드 담당: Android 업로드 흐름을 연결한다 - 검증: URL 발급, PUT 업로드, 완료 등록, 엽서 작성이 순서대로 실행되고 각 단계 실패 메시지가 표시된다.
- [ ] 프론트엔드 담당: 오늘의 엽서 화면에 이미지 표시를 추가한다 - 검증: 이미지가 있는 엽서는 사진과 문장이 함께 보이고, 이미지 없는 엽서는 기존 문장 화면이 유지된다.
- [ ] 문서 담당: `/docs/api.md`를 최신화한다 - 검증: 업로드 요청/응답, 엽서 작성 변경사항, 오류 케이스, 임시 인증 방식이 문서에 포함된다.
- [ ] reviewer 담당: 계획 대비 구현과 리스크를 리뷰한다 - 검증: DDL, API, Android 흐름, 오류 처리, 운영 전환 리스크가 심각도별로 정리된다.

## 구현 순서

1. 백엔드 DDL과 API 계약을 먼저 확정한다 - 검증: 스키마와 요청/응답 예시만 보고 Android가 구현 가능한 상태다.
2. 백엔드 미디어 도메인과 presigned URL 발급/완료 API를 구현한다 - 검증: 단위 테스트 또는 API 호출로 media ID 생성과 완료 상태 전환이 확인된다.
3. 엽서 작성과 오늘의 엽서 조회 응답에 이미지 연결을 붙인다 - 검증: 이미지 없는 기존 텍스트 엽서 흐름이 깨지지 않는다.
4. Android 사진 선택과 업로드 API 클라이언트를 추가한다 - 검증: 선택한 이미지가 업로드 요청 대상으로 전달된다.
5. Android 작성/조회 화면을 이미지 포함 흐름으로 연결한다 - 검증: 에뮬레이터에서 사진 1장과 문장을 포함한 엽서 작성, 배정, 조회가 된다.
6. 문서와 리뷰를 완료한다 - 검증: `/docs/api.md`, `/docs/ddl.sql`, reviewer 결과가 현재 구현과 일치한다.

## 의존성

- 첫 MVP 엽서 작성, 배정, 조회 API가 정상 동작해야 한다.
- 로컬 또는 개발용 S3 호환 오브젝트 스토리지 접근 방식이 필요하다.
- 백엔드가 오브젝트 스토리지에 `HEAD` 요청을 수행할 수 있어야 한다.
- Android는 이미지 선택을 위해 시스템 photo picker 또는 갤러리 접근 방식을 결정해야 한다.
- API base URL과 오브젝트 스토리지 업로드 URL은 개발 환경에서 접근 가능해야 한다.

## 미정 질문

- 로컬 개발에서 실제 AWS S3를 사용할지, LocalStack 또는 MinIO 같은 S3 호환 저장소를 사용할지 결정해야 한다.
- 공개 URL을 사용할 때 버킷을 public으로 둘지, 개발 단계부터 짧은 만료의 signed GET URL을 `image.url`로 생성할지 결정해야 한다.
- 업로드 가능한 최대 byte size를 5MB로 둘지 10MB로 둘지 결정해야 한다.
- 허용할 이미지 content type을 `image/jpeg`, `image/png`, `image/webp`로 제한할지 결정해야 한다.

## 완료 기준

- 사용자가 Android에서 사진 1장과 문장을 함께 엽서로 작성할 수 있다.
- 이미지 업로드는 앱에서 presigned URL로 오브젝트 스토리지에 직접 수행된다.
- 백엔드는 업로드된 이미지 메타데이터와 엽서 연결을 MySQL에 저장한다.
- 오늘의 엽서 배정/조회에서 작성자 식별 정보 없이 사진과 문장이 함께 반환된다.
- 이미지 없는 기존 텍스트 엽서 작성/조회 흐름이 유지된다.
- `/docs/ddl.sql`과 `/docs/api.md`가 구현 상태와 일치한다.
