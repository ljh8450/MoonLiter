# 인증, 기록, 신고, 관리자 승인 확장 계획

## 목표

엽서 수신자가 발신자를 알 수 없는 기본 경험은 유지하면서, 로그인 사용자가 본인이 작성한 엽서와 받은 엽서 기록을 지속적으로 조회하고, 부적절한 엽서를 신고할 수 있게 한다.

또한 엽서는 기본적으로 관리자 승인 후 다른 사용자에게 전달되도록 하고, 관리자가 승인, 반려, 숨김, 신고 처리를 수행할 수 있는 관리자 페이지를 마련한다.

## 맥락

- 초기 MVP는 React + Vite + PWA 웹앱, Supabase Auth, Supabase Postgres, Supabase Storage, Cloudflare Pages 흐름을 기준으로 한다.
- 사진 업로드 세부 계획은 `plan/26-05-16/postcard_photo_upload.md`에서 관리한다.
- 현재 사진 업로드 MVP는 Supabase 소셜/이메일 로그인 기반 작성/수신 흐름으로 전환한다.
- 이 계획은 사진 업로드 MVP 이후 제품 신뢰도와 사용자 기록 기능을 확장하기 위한 후속 구현 단위다.

## 현재 구현 상태

- Supabase 소셜/이메일 로그인은 웹앱에 구현되어 있다.
- 비로그인 익명 작성 기능은 제거하고 소셜/이메일 로그인 기반으로 전환한다.
- 제품의 익명성은 수신자에게 작성자 계정 정보를 노출하지 않는 방식으로 유지한다.
- `postcards.status`는 `pending`, `approved`, `rejected`, `hidden` 값을 지원한다.
- 새 엽서는 `pending`으로 생성되고, `assign_today_postcard()`는 `approved` 상태만 배정한다.
- 작성자 본인의 엽서 조회와 수신자 본인의 delivery 조회를 위한 기본 RLS 정책은 있다.
- 받은 엽서 내용은 오늘의 엽서 화면과 받은 기록 화면에서 확인할 수 있다.
- `postcard_user_actions`, `postcard_reports`, `admin_users` 테이블과 관리자 상태 변경 RPC는 Supabase 마이그레이션에 반영되어 있다.
- 신고 UI와 관리자 페이지는 구현되어 있다.
- 사용자 정지 상태와 정지/해제 RPC는 Supabase 마이그레이션에 반영되어 있다.
- PWA 배포 캐시는 서비스 워커 내비게이션 네트워크 우선 처리와 Cloudflare Pages `_headers`로 정리되어 있다.
- 고아 파일 정기 정리는 아직 구현되지 않았다.

## 범위

- 인증
  - 이메일 매직 링크, 이메일/비밀번호, 구글 로그인, 카카오 로그인을 모두 구현 대상으로 둔다.
  - 구현 순서는 이메일 매직 링크, 이메일/비밀번호, 구글 로그인, 카카오 로그인 순서로 진행한다.
  - 비로그인 익명 작성 기능은 제공하지 않는다.
  - 작성 기록과 받은 엽서 기록은 로그인 계정 기준으로 지속 저장한다.
- 익명성
  - 작성과 수신에는 로그인이 필요하다.
  - 수신자는 엽서 작성자의 계정, 이름, 이메일, 소셜 프로필을 볼 수 없다.
  - 작성자 본인은 로그인 후 본인이 작성한 엽서 기록을 볼 수 있다.
  - 수신자 본인은 로그인 후 본인이 받은 엽서 기록을 볼 수 있다.
- 기록
  - 작성한 엽서 목록과 상세 조회를 제공한다.
  - 받은 엽서 목록과 상세 조회를 제공한다.
  - 이미지가 있는 엽서는 signed URL 조회 방식을 유지한다.
- 신고
  - 사용자는 받은 엽서에 관심없음, 숨김, 신고 액션을 수행할 수 있다.
  - 관심없음은 사용자 개인 선호 신호로 기록한다.
  - 숨김은 해당 사용자의 받은 기록과 화면에서만 제외하며, 엽서 자체 상태는 변경하지 않는다.
  - 신고는 관리자 사후 검토 대상으로 기록한다.
  - 신고 사유, 신고자, 대상 엽서, 처리 상태를 기록한다.
- 관리자 승인
  - 새 엽서는 기본적으로 `pending` 상태로 생성된다.
  - 관리자 승인 전에는 랜덤 전달 대상에 포함하지 않는다.
  - 관리자는 모든 새 엽서를 1차로 검수하고 승인 또는 반려 처리한다.
  - 승인된 엽서만 다른 사용자에게 전달될 수 있다.
  - 관리자는 신고된 승인 엽서를 사후 검토하고 유지 또는 숨김 처리할 수 있다.
- 관리자 페이지
  - 관리자만 접근 가능한 웹 관리 화면을 제공한다.
  - 대기 중 엽서 목록, 신고 목록, 엽서 상세, 승인/반려/숨김/신고 처리 액션을 제공한다.
  - 올바르지 않은 사용자를 정지하거나 정지 해제할 수 있다.
- 고아 파일 정리
  - 사진 업로드 MVP에서 DB insert 실패 시 즉시 cleanup을 시도하되, 남은 고아 파일의 정기 정리는 이 확장 계획에서 구현한다.
  - Storage path와 DB의 `image_path`를 비교해 연결되지 않은 오래된 object를 정리하는 운영 흐름을 마련한다.

## 제외 범위

- 실명 기반 공개 프로필.
- 수신자에게 작성자 닉네임이나 계정 정보를 표시하는 기능.
- 사용자 간 차단 기능.
- 관리자용 고급 통계 대시보드.
- 자동 이미지/텍스트 AI 검수.
- 관리자 다중 역할과 세분화된 권한 체계.
- 고객센터형 신고 이의제기 워크플로.
- 푸시 알림, 이메일 알림, 카카오 알림톡.
- Android/iOS 관리자 화면.

## 의존성

- Supabase Auth 설정이 가능해야 한다.
- 구글과 카카오 소셜 로그인을 사용할 수 있도록 각 provider 앱 등록과 redirect URL 설정이 필요하다.
- 작성/수신 기록을 저장할 Supabase Postgres 스키마와 RLS 정책이 필요하다.
- 별도 관리자 테이블을 기준으로 관리자 권한을 식별할 수 있어야 한다.
- 관리자 상태 변경은 직접 테이블 업데이트보다 `approve_postcard`, `reject_postcard`, `hide_postcard`, `resolve_postcard_report` 같은 RPC로 제한한다.
- 사용자 정지 처리는 `suspend_user`, `unsuspend_user` RPC로 제한한다.
- 승인 전 엽서를 랜덤 전달 대상에서 제외하는 조회 조건은 `assign_today_postcard()`에 반영되어 있다.
- Storage object 목록과 DB `image_path`를 비교할 수 있는 정리 권한 또는 운영 작업 경로가 필요하다.

## 미정 질문

- 이메일/비밀번호 로그인에서 이메일 인증을 필수로 둘지 결정해야 한다.
- 관리자 승인 SLA나 운영 기준을 둘지 결정해야 한다.
- 반려된 엽서를 작성자에게 보여줄지, 반려 사유를 제공할지 결정해야 한다.
- 고아 파일을 어느 보존 기간 이후 삭제할지 결정해야 한다.

## 완료 기준

- 수신자는 엽서 작성자를 식별할 수 없다.
- 이메일 매직 링크, 이메일/비밀번호, 구글, 카카오 로그인 흐름을 순차적으로 사용할 수 있다.
- 로그인 사용자는 본인이 작성한 엽서와 받은 엽서 기록을 볼 수 있다.
- 작성 기록과 받은 기록은 로그인 계정 기준으로 지속 저장된다.
- 사용자는 받은 엽서에 관심없음, 숨김, 신고 액션을 수행할 수 있다.
- 새 엽서는 관리자 승인 전까지 다른 사용자에게 전달되지 않는다. 이 조건은 현재 DB/RPC에 반영되어 있다.
- 관리자는 관리자 페이지에서 새 엽서를 1차 검수해 승인 또는 반려하고, 신고된 엽서를 사후 검토해 유지 또는 숨김 처리할 수 있다.
- 관리자는 올바르지 않은 사용자를 정지하거나 정지 해제할 수 있다.
- DB에 연결되지 않은 오래된 Storage object 정리 기준이 마련되어 있다.
- 관련 스키마, RLS, 데이터 흐름 문서, reviewer 결과가 구현 상태와 일치한다.
