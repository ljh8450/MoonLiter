# 인증, 기록, 신고, 관리자 승인 확장 계획

## 목표

엽서 수신자가 발신자를 알 수 없는 기본 경험은 유지하면서, 로그인 사용자가 본인이 작성한 엽서와 받은 엽서 기록을 조회하고, 부적절한 엽서를 신고할 수 있게 한다.

또한 엽서는 기본적으로 관리자 승인 후 다른 사용자에게 전달되도록 하고, 관리자가 승인, 반려, 숨김, 신고 처리를 수행할 수 있는 관리자 페이지를 마련한다.

## 맥락

- 초기 MVP는 React + Vite + PWA 웹앱, Supabase Auth, Supabase Postgres, Supabase Storage, Cloudflare Pages 흐름을 기준으로 한다.
- 사진 업로드 세부 계획은 `plan/26-05-16/postcard_photo_upload.md`에서 관리한다.
- 현재 사진 업로드 MVP는 Supabase 익명 로그인 기반 작성/수신 흐름을 우선 검증한다.
- 이 계획은 사진 업로드 MVP 이후 제품 신뢰도와 사용자 기록 기능을 확장하기 위한 후속 구현 단위다.

## 현재 구현 상태

- Supabase 익명 로그인은 웹앱에 구현되어 있다.
- `postcards.status`는 `pending`, `approved`, `rejected`, `hidden` 값을 지원한다.
- 새 엽서는 `pending`으로 생성되고, `assign_today_postcard()`는 `approved` 상태만 배정한다.
- 작성자 본인의 엽서 조회와 수신자 본인의 delivery 조회를 위한 기본 RLS 정책은 있다.
- 받은 엽서 내용은 오늘의 엽서 화면에서만 확인할 수 있으며, 작성/수신 기록 목록 화면은 아직 없다.
- 신고 테이블, 신고 UI, 관리자 권한 모델, 관리자 페이지, 고아 파일 정기 정리는 아직 구현되지 않았다.

## 범위

- 인증
  - 자체 로그인과 소셜 로그인 후보를 정리한다.
  - 이메일 로그인 또는 이메일 매직 링크 구현은 이 계획의 인증 확장 범위에서 다룬다.
  - 소셜 로그인 후보는 카카오와 구글을 우선 검토한다.
  - 익명 사용자가 로그인으로 전환할 때 기존 작성/수신 기록을 연결할지 결정한다.
- 익명성
  - 수신자는 엽서 작성자의 계정, 이름, 이메일, 소셜 프로필을 볼 수 없다.
  - 작성자 본인은 로그인 후 본인이 작성한 엽서 기록을 볼 수 있다.
  - 수신자 본인은 로그인 후 본인이 받은 엽서 기록을 볼 수 있다.
- 기록
  - 작성한 엽서 목록과 상세 조회를 제공한다.
  - 받은 엽서 목록과 상세 조회를 제공한다.
  - 이미지가 있는 엽서는 signed URL 조회 방식을 유지한다.
- 신고
  - 사용자는 받은 엽서를 신고할 수 있다.
  - 신고 사유, 신고자, 대상 엽서, 처리 상태를 기록한다.
  - 신고된 엽서는 관리자 처리 전까지 노출 정책을 명확히 정한다.
- 관리자 승인
  - 새 엽서는 기본적으로 `pending` 상태로 생성된다.
  - 관리자 승인 전에는 랜덤 전달 대상에 포함하지 않는다.
  - 관리자는 엽서를 승인, 반려, 숨김 처리할 수 있다.
- 관리자 페이지
  - 관리자만 접근 가능한 웹 관리 화면을 제공한다.
  - 대기 중 엽서 목록, 신고 목록, 엽서 상세, 승인/반려/숨김/신고 처리 액션을 제공한다.
- 고아 파일 정리
  - 사진 업로드 MVP에서 DB insert 실패 시 즉시 cleanup을 시도하되, 남은 고아 파일의 정기 정리는 이 확장 계획에서 구현한다.
  - Storage path와 DB의 `image_path`를 비교해 연결되지 않은 오래된 object를 정리하는 운영 흐름을 마련한다.

## 제외 범위

- 실명 기반 공개 프로필.
- 수신자에게 작성자 닉네임이나 계정 정보를 표시하는 기능.
- 관리자용 고급 통계 대시보드.
- 자동 이미지/텍스트 AI 검수.
- 관리자 다중 역할과 세분화된 권한 체계.
- 고객센터형 신고 이의제기 워크플로.
- 푸시 알림, 이메일 알림, 카카오 알림톡.
- Android/iOS 관리자 화면.

## 구현 순서

1. 익명성 원칙과 인증 도입 범위를 먼저 확정한다 - 검증: 수신자가 작성자를 식별할 수 없는 정보 경계와 1차 로그인 방식이 문서화된다.
2. 데이터 모델과 RLS 정책을 설계한다 - 검증: 작성자 기록, 수신자 기록, 관리자 권한, 신고, 엽서 승인 상태가 서로 권한 충돌 없이 표현된다.
3. 엽서 승인 상태를 작성/전달 흐름에 반영한다 - 상태: DB/RLS/RPC 반영 완료, 관리자 처리 UI 미완료.
4. 이메일 로그인 또는 이메일 매직 링크와 계정 전환 흐름을 구현한다 - 검증: 사용자가 선택한 인증 방식으로 로그인할 수 있고 익명 세션 기록 연결 여부가 결정된 정책대로 동작한다.
5. 작성한 엽서와 받은 엽서 기록 화면을 구현한다 - 검증: 로그인 사용자가 본인 소유의 작성/수신 기록만 조회하고, 수신자는 작성자 식별 정보를 볼 수 없다.
6. 신고 기능을 구현한다 - 검증: 받은 엽서에서 신고를 생성할 수 있고 신고 상태가 관리자 처리 전까지 추적된다.
7. 관리자 페이지를 구현한다 - 검증: 관리자만 대기 엽서와 신고 목록에 접근하고 승인, 반려, 숨김, 신고 처리 액션을 수행할 수 있다.
8. 고아 파일 정리 운영 흐름을 구현한다 - 검증: DB에 연결되지 않은 오래된 Storage object를 식별하고 삭제할 수 있다.
9. 문서와 리뷰를 완료한다 - 검증: `/docs/ddl.sql`, 데이터 흐름 문서, reviewer 결과가 인증, 기록, 신고, 관리자 승인 구현과 일치한다.

## 의존성

- Supabase Auth 설정이 가능해야 한다.
- 카카오 또는 구글 소셜 로그인을 사용할 경우 각 provider 앱 등록과 redirect URL 설정이 필요하다.
- 작성/수신 기록을 저장할 Supabase Postgres 스키마와 RLS 정책이 필요하다.
- 관리자 권한을 식별할 방법이 필요하다.
- 승인 전 엽서를 랜덤 전달 대상에서 제외하는 조회 조건은 `assign_today_postcard()`에 반영되어 있다.
- Storage object 목록과 DB `image_path`를 비교할 수 있는 정리 권한 또는 운영 작업 경로가 필요하다.

## 미정 질문

- 자체 로그인은 이메일/비밀번호, 이메일 매직 링크, 또는 다른 방식 중 무엇으로 제공할지 결정해야 한다.
- 카카오와 구글 중 어느 소셜 로그인을 먼저 구현할지 결정해야 한다.
- 익명으로 작성한 엽서를 로그인 후 계정에 연결할지 결정해야 한다.
- 받은 엽서 기록은 로그인 이후 받은 엽서만 저장할지, 익명 세션의 받은 엽서도 로그인 시 연결할지 결정해야 한다.
- 관리자 권한은 Supabase Auth user metadata, 별도 관리자 테이블, 또는 외부 관리자 인증 중 무엇으로 관리할지 결정해야 한다.
- 신고된 엽서를 관리자 처리 전까지 즉시 숨길지, 누적 신고 수 기준으로 숨길지 결정해야 한다.
- 관리자 승인 SLA나 운영 기준을 둘지 결정해야 한다.
- 반려된 엽서를 작성자에게 보여줄지, 반려 사유를 제공할지 결정해야 한다.
- 고아 파일을 어느 보존 기간 이후 삭제할지 결정해야 한다.

## 완료 기준

- 수신자는 엽서 작성자를 식별할 수 없다.
- 로그인 사용자는 본인이 작성한 엽서와 받은 엽서 기록을 볼 수 있다.
- 사용자는 받은 엽서를 신고할 수 있다.
- 새 엽서는 관리자 승인 전까지 다른 사용자에게 전달되지 않는다. 이 조건은 현재 DB/RPC에 반영되어 있다.
- 관리자는 관리자 페이지에서 엽서를 승인, 반려, 숨김 처리하고 신고를 처리할 수 있다.
- DB에 연결되지 않은 오래된 Storage object를 정리할 수 있다.
- 관련 스키마, RLS, 데이터 흐름 문서가 구현 상태와 일치한다.
